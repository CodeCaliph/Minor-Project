Introduction

  • Most real tables have gaps. A sensor stops working, a patient skips a test, or someone leaves a form field blank.
  • If the gaps are filled badly, every model trained on that data carries the mistake forward.
  • Traditional methods (mean, k-NN, MICE, MissForest) fill gaps using patterns in the numbers alone.
TypeWhat it meansExample
MCAR – Missing Completely At RandomThe gap has nothing to do with any valueA lab machine fails on random days
MAR – Missing At RandomThe gap depends on other values we can seeOlder patients skip a fitness test more often
MNAR – Missing Not At RandomThe gap depends on the missing value itselfPeople with very high income don't report it
Table 1: Types of missing data (Rubin, 1976)

Almost every real dataset has missing values. And whatever we do to fill them affects everything built on top of that data.

Rubin described three types. MCAR is pure chance. MAR is when the gap depends on something else we can see, like age. MNAR is the tricky one: the value is missing because of what it is. Rich people not reporting income is the classic example. MNAR is the hardest case and it shows up a lot in our project.

Introduction (Contd.)

  • With LLMs, a row is written out as text and the model guesses the missing value, roughly the way a person would.
  • Papers report good results for filling gaps [1, 2, 5], building cleaning workflows [3] and spotting errors [9].
  • But most of these tests use famous datasets like Iris, Pima and Adult.
  • LLMs can recite many of these datasets from memory [4].
  • So did the model understand the data, or just remember it?
Figure 1: An overview of CRILM, an LLM-based imputation method (redrawn from Hayat and Hasan [1])

This figure is from CRILM, one of our base papers. They describe the dataset and the missing column to a big LLM, the LLM writes a short description for each missing value, and then a small model is fine-tuned on that text.

It works well on paper. But the datasets they used, like Iris and Wine, are all over the internet. Bordt et al. showed GPT-4 can type out the Iris dataset almost row by row. So we can't tell whether the LLM is reasoning or recalling. That's the question our project is built around.

Problem Statement

  • Papers say LLMs fill missing values better than classical methods.
  • But they test on datasets the LLM has probably already seen during training.
  • So a good score can mean two very different things: the model understood the data, or it simply remembered the records.
  • Until we can tell these apart, we can't trust LLM cleaning on private data like hospital or bank records.
  • Our aim: build a fair test bench that changes one thing at a time (where the data comes from, and what the columns are called) and see how the LLM's accuracy moves.

The core problem is that a high score is ambiguous. If an LLM fills Pima's missing glucose values correctly, maybe it knows medicine, or maybe it saw Pima in its training data.

That matters because the places that really need data cleaning, like hospitals and banks, have private data the model has never seen. If the LLM's advantage is just memory, it won't help them.

A recent study by Mangussi et al. noticed LLMs beat MICE on real data but lose on synthetic data. But their synthetic data had no meaningful column names and also couldn't have been memorised, so you can't tell which of the two caused it. We change one thing at a time.

RQ1 is the main one. RQ2 asks whether memorisation scores line up with performance. RQ3 is our MNAR test, which I'll explain with the formulas.

RQ4 and RQ5 are side questions. RQ4 is about whether synthetic data could replace private data for comparing methods. RQ5 is about whether the usual way of faking MNAR leaks the answer.

UniDM rewrites rows as sentences so they look like the text the model was trained on. That's basically trying to trigger the model's memory, which is interesting for us.

Literature Review (Contd.)

What the papers got right

01LLMs can fill in missing values and tidy messy tables, often better than older methods.
02You don't need a giant model. 7–9B models running on a normal GPU do well.
03Showing the model a few example rows, or letting it work in steps, helps a lot.
04Column names matter. Hide them and accuracy drops sharply.

What's still missing

01Almost nobody checks whether the model has already seen the test data.
02Good results are credited to the model's "knowledge" without proof.
03Some papers report the biggest LLM gains under MNAR; the most careful study found them inconsistent.
04Tests use small, famous datasets with only a few repeat runs.

After reading all nine papers, this is our takeaway. On the good side: LLMs clearly help, small models are enough, examples help, and column names carry a lot of the signal.

On the other side: eight of the nine papers never check for memorisation, even though several say their results come from "prior knowledge". And the MNAR picture isn't settled. CRILM and LLM-Forest report their biggest gains under MNAR, around 10 points. Abate et al., with stricter testing, found MNAR results inconsistent; on binary columns plain median/mode was actually best.

Research Gap

  • Most papers test LLM cleaners on famous datasets like Iris, Pima and Adult.
  • Bordt et al. [4] showed LLMs can recite such datasets from memory, and that this inflates their scores.
  • Yet none of the cleaning papers checks for this, hides the column names, or tests on data the model couldn't have seen.
  • Bordt et al. only looked at classification, not at filling missing values or at MNAR.
  • So we still don't know how much of an LLM's cleaning skill is real understanding and how much is memory.

Put the two halves of the literature side by side and the gap is obvious. One group says LLMs are great at cleaning, using famous datasets. Another paper proves LLMs memorise famous datasets. Nobody has connected the two.

That's what our project does: same data, same missing cells, but we take away memory, or meaning, one at a time and watch what happens.

3 × 3 = 9 versions of every dataset. We hide 10%, 20% or 30% of the values in exactly the same cells in all 9, so any change in accuracy comes from the version alone.

This is the trick that makes the whole project work. Every dataset becomes nine versions.

On the left, we change where the data comes from. The perturbed copy still has the real structure but doesn't match anything the model memorised. The synthetic twin has the same patterns but completely new rows.

On the right, we change the column names. Real names, f1 f2 f3, or names swapped around so they're misleading.

And because the missing cells are the same in all nine, if the LLM suddenly gets worse on the twin, it can only be because it lost something to remember.

Proposed Algorithm

Every method gets the same puzzle. We change one thing at a time and watch whose accuracy drops.

  1. Collect datasets. Famous ones (Iris, Wine, Breast Cancer, Pima) and a new one (DiaBD).
  2. Test memorisation. Check how much of each dataset every LLM can recite, using tabmemcheck.
  3. Make 9 versions. Real, perturbed and synthetic twin, each with real, hidden and shuffled column names.
  4. Hide values. Remove 10–30% of cells (MCAR, MAR, MNAR, real Pima patterns), the same cells in all 9 versions.
  5. Fill the gaps. Classical methods and local 4-bit LLMs, with zero-shot, few-shot and step-by-step prompts.
  6. Compare results. Measure the error against the true values and work out the two effects.
Figure 7: Steps at a glance

Here is the method in six steps. The flowchart on the right is the same thing at a glance.

First we pick the datasets and test how much each model remembers them. Then each dataset becomes nine versions, we hide the same cells in all nine, and both the classical methods and the LLMs fill them in. Finally we compare against the true values.

The LLMs run locally in 4-bit on a free GPU: Llama 3.1 8B, Qwen2.5 at 3, 7 and 14B, and Gemma 2 9B. We try them with no examples, with four example rows, and with the step-by-step method from Abate et al.

Algorithm 1  Benchmark procedure
1Input: datasets D, classical methods C, LLMs M
2for each dataset d ∈ D do
3score memorisation of d for each model in M
4V ← 9 versions of d (3 origins × 3 name styles)
5for each mechanism g, rate r ∈ {10, 20, 30}% do
6mask ← hide cells using g, r // shared by all of V
7for each v ∈ V, method m ∈ C ∪ M do
8fill hidden cells of v with m
9record NRMSE, MAE, cost
10compute Δmem, Δsem and Dm using (1)–(3)
11Output: effect sizes and method rankings

Key formulations

Δmem = [ELLM(twin) − ELLM(real)] − [ECL(twin) − ECL(real)](1)

Extra error the LLM suffers when there is nothing to recall.

Δsem = [ELLM(hidden) − ELLM(names)] − [ECL(hidden) − ECL(names)](2)

Extra error the LLM suffers when column names are hidden.

Dm = Em(MNAR) − Em(MCAR)(3)

How much method m worsens under MNAR. Small on real data but large on the twin points to memorisation.

E = NRMSE of a method  ·  CL = classical method  ·  twin = synthetic copy

On the left is the same procedure written as pseudocode. The important line is 6: the mask is made once and shared by all nine versions.

On the right are the three quantities we compute. Equation 1: how much worse the LLM gets on the synthetic twin, minus how much worse a classical method gets. Classical methods cannot memorise, so the second bracket only removes any change in difficulty. What is left came from memory. Equation 2 is the same idea with hidden column names.

Equation 3 is our MNAR fingerprint. Under MNAR the hidden values are unusual, so a method that really infers must get worse. If an LLM barely gets worse on Pima but clearly does on the twin of Pima, it was probably remembering.

Proposed Architecture

  • Datasets are loaded and kept complete, so the true values are always known.
  • Memorisation test scores how well each LLM can recite each dataset.
  • Version maker creates the 9 versions.
  • Mask generator hides the same cells in every version.
  • Imputers: classical methods and local LLMs fill the gaps. LLM answers go through a parser.
  • Evaluator compares filled values with the true ones, and the analysis step works out the effects.
Figure 8: System architecture

Here's how the system is built. Data flows left to right.

The datasets go into the version maker, then the mask generator hides cells. The masked tables go to two engines in parallel: the classical imputers, and the LLM engine, which builds a prompt, runs the model locally through Ollama and parses the answer.

Two dotted lines matter. The top one carries the true values straight to the evaluator; they're never shown to the imputers. The bottom one carries the memorisation scores to the analysis step, so we can check whether more memory means better scores.

Performance Evaluation

What we checkHow
Accuracy of filled valuesNRMSE* and MAE* for numbers, % correct for categories
Shape of the dataHow close the filled values' distribution is to the real one
UsefulnessAccuracy of random forest, gradient boosting and logistic regression trained on the cleaned data
CostModel calls, tokens, time and invalid answers
Table 6: Evaluation metrics
NRMSE = √( 1⁄n Σ (x̂i − xi)² ) / s       MAE = 1⁄n Σ |x̂i − xi|

* x̂i = value filled in by the method, xi = true value, n = number of hidden cells, s = spread of the column (range or standard deviation, to be fixed during implementation).

Since we hide the values ourselves, we know the right answer for every cell. So we can measure the error directly.

MAE is the average distance from the true value. NRMSE is similar but punishes big misses more, and dividing by the spread lets us compare columns with different units.

We also check the distribution, because always guessing the average can give a decent error but ruins the data. And precision or recall don't really apply here, since we're filling values, not classifying.

Performance Evaluation (Contd.)

How we'll test

  • Baselines: mean, median, k-NN, MICE, MissForest
  • 5 LLMs, each with 3 prompting styles (no examples, 4 examples, step by step)
  • Every setting repeated with different random seeds
  • Paired permutation tests with Holm–Bonferroni correction, Hedges' g and bootstrap confidence intervals
